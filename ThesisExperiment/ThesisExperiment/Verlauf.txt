Verlauf / Experiment-Log
========================

Dieses Dokument protokolliert alle bisher durchgefuehrten Schritte des
Thesis-Experiments. Das Experiment untersucht, ob ein Large Language Model
sinnvolle Unit-Tests fuer C#-Methoden aus realen Open-Source-Projekten
generieren kann. Verglichen werden drei Varianten:

  - Variante A (Baseline): Vorhandene, menschengeschriebene Tests
  - Variante B (Single-Shot): Ein einzelner LLM-Prompt erzeugt den Test
  - Variante C (Repair-Loop): Iterative Generierung mit bis zu 3 Versuchen,
    wobei Fehlermeldungen als Feedback zurueckgefuehrt werden

Die Pipeline besteht aus 8 Schritten (Steps 1-8), von denen bisher
die ersten fuenf abgeschlossen wurden.

Step 1 - Projektauswahl (select-projects)
------------------------------------------------------------------------

Befehl:   dotnet run -- select-projects --output appendix

Beschreibung:
  Der Befehl durchsucht GitHub ueber die REST-API nach C#-Repositories mit
  mehr als 50 Sternen. Fuer jedes gefundene Repository wird automatisch
  folgendes geprueft:

    1. Git-Clone des Repos in den lokalen Ordner "repos/"
    2. Build-Versuch mit "dotnet build"
    3. Erkennung von Test-Projekten (xUnit, NUnit, MSTest)
    4. Zaehlung der oeffentlichen Methoden via Roslyn-Analyse
    5. Zaehlung der C#-Codezeilen (LOC)

  Ein Projekt besteht die Filter, wenn:
    - Der Build erfolgreich ist
    - Mindestens 1 Test-Projekt vorhanden ist
    - Mindestens 10 oeffentliche Methoden existieren
    - Mindestens 1000 Zeilen C#-Code vorhanden sind

Step 4 - Modellwahl: Upgrade von GPT-3.5-Turbo auf GPT-5-mini
------------------------------------------------------------------------

Begruendung:
  Das urspruenglich im Code hardcodierte Modell "gpt-3.5-turbo" ist fuer eine
  Bachelorarbeit im Jahr 2026 nicht mehr zeitgemaess. Ein Pruefer koennte die
  Relevanz der Ergebnisse anzweifeln, wenn ein veraltetes Modell verwendet wird.

  Daher wurde eine Modellanalyse durchgefuehrt, um das optimale Modell fuer
  die Unit-Test-Generierung zu bestimmen.

Modellvergleich (Stand Januar 2026):

  Modell              | Preis/1M Tokens    | Staerken
                      | (Input / Output)   |
  --------------------|--------------------|-----------------------------------------
  gpt-5.2             | $1.75 / $14.00     | Bestes Coding/Agentic, sehr komplex
  gpt-5.1-codex       | $1.25 / $10.00     | Fuer lange Coding-Workflows optimiert
  gpt-5-mini          | $0.25 / $2.00      | Sehr gutes Preis-Leistungs-Verhaeltnis
  gpt-5.1-codex-mini  | $0.25 / $2.00      | Codex-optimiert, gut fuer CI
  gpt-5-nano          | $0.05 / $0.40      | Ultra-guenstig, fuer einfache Tasks

Entscheidung:
  Fuer die Bachelorarbeit wird "gpt-5-mini" als primaeres Modell verwendet.

  Gruende:
    1. Kosteneffizienz: Bei 50 Methoden x 3 Varianten (mit bis zu 3 Repair-
       Versuchen in Variante C) summieren sich die API-Calls schnell.
       Mit gpt-5-mini bleiben die Kosten ueberschaubar.

    2. Praxisnaehe: In der Realitaet wuerden Entwickler im CI eher ein
       kostenguenstiges Modell einsetzen, nicht das teuerste.

    3. Wissenschaftliche Aussagekraft: Wenn ein guenstiges Modell bereits
       gute Ergebnisse liefert, ist das eine staerkere Aussage. Wenn es
       scheitert, ist das ebenfalls ein valides Forschungsergebnis.

    4. Aktualitaet: GPT-5-mini ist ein aktuelles Modell (2026), wodurch
       die Thesis-Ergebnisse relevant und zeitgemaess sind.

Technische Umsetzung:
  Die Aenderung erfolgt in einer einzigen Datei:
    - Services/OpenAiService.cs, Zeile 32
    - Alt: _chatClient = new ChatClient(model: "gpt-3.5-turbo", ...)
    - Neu: _chatClient = new ChatClient(model: "gpt-5-mini", ...)

API-Test:
  Vor der Aenderung wurde die OpenAI-API mit dem vorhandenen Key getestet.
  Der Test war erfolgreich (Modell antwortete korrekt).

  Nach der Aenderung wurde ein erneuter Test mit gpt-5-mini durchgefuehrt:
    - Ergebnis: ERFOLGREICH
    - Modell-ID (von API zurueckgegeben): gpt-5-mini-2025-08-07
    - Das Modell ist einsatzbereit fuer die Testgenerierung.

Status: ABGESCHLOSSEN

Durchgefuehrte Aenderungen:

Step 5 - Methoden-Sampling (sample-methods)
------------------------------------------------------------------------

Befehl:   dotnet run -- sample-methods --output appendix

Beschreibung:
  Dieser Schritt waehlt deterministisch 5 Projekte aus der gefilterten Liste
  und samplet pro Projekt genau 10 oeffentliche Methoden fuer das Experiment.

  Algorithmus:
    1. Projekte nach repo_url alphabetisch sortieren
    2. Fisher-Yates-Shuffle mit festem Seed (42) fuer Reproduzierbarkeit
    3. Iteriere durch geshuffelte Projekte bis 5 valide gefunden
    4. Pro Projekt: Methoden extrahieren, alphabetisch sortieren, shufflen
    5. Erste 10 Methoden pro Projekt samplen

  Exclusion-Kriterien fuer Dateien:
    - bin/, obj/, generated/, migrations/ (Build-Artefakte)
    - *test*, *tests, unittest, *.test, *.tests (Test-Code)
    - *spec*, specs, *.spec (Spec-Dateien)

  Exclusion-Kriterien fuer Methoden:
    - Equals, GetHashCode, ToString (Standard-Overrides)
    - Methoden in nicht-oeffentlichen Typen

  Implementierte Fixes vor Ausfuehrung:
    - Fix 1: Garantiert 5 valide Projekte (iteriert weiter bei Skips)
    - Fix 2: CSV Commit Hash als Source of Truth (mit checkout)
    - Fix 3: Duplicate Check auf (RepoUrl, Identifier) Tuple

Durchfuehrung:

  Erster Lauf (mit Fixes 1-3):
    Nach manueller Validierung der method_list_all.csv wurden 10/50 Methoden
    aus Test-Ordnern gefunden:
      - duplicati: 2 (Duplicati.Browser.Test/, UnitTest/)
      - Kavita: 5 (API.Tests/)
      - UniTask: 3 (UniTask.NetCoreTests/)

    Ursache: Die ShouldExcludeFile-Methode pruefte nur auf "/test" und "/spec"
    als Substring, erfasste aber nicht Muster wie "API.Tests", "UnitTest" oder
    "*.NetCoreTests".

  Fix 4 - Robustere Test-Exclusion:
    Die ShouldExcludeFile-Methode wurde auf segment-basierte Pruefung umgestellt:
      - Pfad wird in Segmente aufgeteilt (statt Substring-Match)
      - Erfasst: *test, *tests, unittest, *.test, *.tests
      - Erfasst: spec, specs, *spec, *.spec
      - Case-insensitive pro Segment

    Geaenderte Datei: Commands/SampleMethodsCommand.cs (Zeilen 237-267)

  Zweiter Lauf (mit Fix 4):
    Ergebnis: 0/50 Methoden aus Test-Pfaden
    Validierung: grep "test" method_list_all.csv -> keine Treffer

Teil A: Implementierte Infrastructure-Fixes
========================================================================

1. dotnet tool restore fuer Stryker (StrykerService.cs)
   ---------------------------------------------------------
   Problem:
     Bei Polly schlug Stryker fehl mit der Meldung "dotnet tool restore"
     benoetigt. Stryker ist als lokales dotnet-Tool konfiguriert
     (.config/dotnet-tools.json), muss aber vor der Ausfuehrung
     wiederhergestellt werden.

   Loesung:
     - Neue Methode EnsureToolRestoreAsync() in StrykerService.cs
     - Prueft ob .config/dotnet-tools.json existiert
     - Fuehrt "dotnet tool restore" einmalig pro Repo aus
     - Tracking via HashSet<string> _toolRestoredRepos
     - Fehler werden geloggt aber nicht abgebrochen (soft fail)

   Geaenderte Dateien:
     - Services/StrykerService.cs (Zeilen 93-131)

2. test.runsettings fuer Locale-Konsistenz (DotnetTestService.cs)
   ---------------------------------------------------------
   Problem:
     Tests schlugen fehl wegen Locale-Unterschieden, z.B.:
       - duplicati: "Size: 1.5 KB" vs "Size: 1,5 KB"
       - Testausgabe auf Deutsch statt Englisch

   Loesung:
     - Neue Datei test.runsettings mit Environment-Variablen:
         LANG=en_US.UTF-8
         LC_ALL=en_US.UTF-8
         DOTNET_CLI_UI_LANGUAGE=en
     - DotnetTestService sucht automatisch nach test.runsettings
     - Wird via --settings Flag an dotnet test uebergeben
     - Fallback auf Projekt-Verzeichnis fuer Development

   Geaenderte/Neue Dateien:
     - test.runsettings (NEU)
     - ThesisExperiment.csproj (Content-Include fuer runsettings)
     - Services/DotnetTestService.cs (Konstruktor + beide Methoden)

   Hinweis:
     Die runsettings-Datei aendert die CLI-Sprache, aber nicht die
     Anwendungskultur im Test-Prozess. Einige Locale-abhaengige
     Tests (z.B. Zahlenformatierung) schlagen weiterhin fehl.
     Das ist ein Projekt-internes Problem, nicht unsere Pipeline.

3. Stryker Budget-Skip Rule (StrykerService.cs)
   ---------------------------------------------------------
   Problem:
     Bei duplicati hat Stryker 10 Source-Files, jedes mit 10 Min Timeout.
     Das fuehrt zu ~100 Minuten Wartezeit ohne nuetzliche Daten.

   Loesung:
     - Nach 2 aufeinanderfolgenden Timeouts fuer ein Repo werden
       alle weiteren Stryker-Aufrufe uebersprungen
     - Tracking via Dictionary<string, int> _consecutiveTimeouts
     - Tracking via HashSet<string> _budgetExceededRepos
     - MutationResult.Status = "skipped_budget" mit Note

   Neue Status-Werte fuer MutationResult.Status:
     - "available": Stryker erfolgreich ausgefuehrt
     - "timeout": Stryker Timeout (einzelne Datei)
     - "skipped_budget": Uebersprungen nach 2 Timeouts
     - "error": Stryker-Fehler (Exit Code != 0, Exception, etc.)

   Geaenderte Dateien:
     - Models/MutationResult.cs (Status + Note Felder)
     - Services/StrykerService.cs (komplette Ueberarbeitung)
     - Models/RunFlatRow.cs (MutationStatus fuer CSV)
     - Commands/AggregateResultsCommand.cs (MutationStatus-Mapping)
     - Commands/LabelErrorsCommand.cs (MutationStatus-Mapping)
     - Commands/CollectBaselineCommand.cs (neue API-Signatur)
     - Commands/RunSingleShotCommand.cs (neue API-Signatur)

    #pragma warning disable OPENAI001 // Experimental API
    var options = new ChatCompletionOptions
    {
        MaxOutputTokenCount = 4096,
        ReasoningEffortLevel = ChatReasoningEffortLevel.Low
    };
    #pragma warning restore OPENAI001

Zusammenfassung des Experiments
------------------------------------------------------------------------

Das Experiment ist nun vollstaendig abgeschlossen. Alle drei Varianten
wurden auf 50 Methoden aus 5 Open-Source C#-Projekten angewendet:

  Variante A (Baseline):     50 Records - Menschengeschriebene Tests
  Variante B (Single-Shot):  54 Records - Ein LLM-Prompt pro Methode
  Variante C (Repair-Loop):  38 Records - Bis zu 3 Reparaturversuche

Hauptergebnisse:
  - LLM-generierte Tests kompilieren in nur ~16% der Faelle
  - Von den kompilierenden Tests erreichen nur ~5% echte Coverage
  - Das "Kopie-Problem" ist ein systematisches LLM-Verhaltensmuster
  - Der Repair-Loop verdreifacht die Token-Kosten bei minimalem Nutzen
  - Projektkomplexitaet ist der wichtigste Erfolgspraediktor

Alle Rohdaten liegen als JSON-RunRecords vor und koennen fuer die
statistische Auswertung in der Thesis verwendet werden.
